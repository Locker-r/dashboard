# Reactivation Desk: утверждённые бизнес-правила

Этот документ фиксирует целевые правила приложения. Часть правил ещё не реализована в текущем браузерном прототипе. Клиентские проверки не являются границей безопасности: настоящая защита должна быть реализована на backend через Auth, RLS и атомарные RPC/транзакции.

## Пользователи и роли

- Роли: `admin` и `agent`.
- Сотрудников создаёт только администратор; открытой регистрации нет.
- В системе может быть несколько администраторов.
- Последнего активного администратора нельзя удалить, деактивировать или понизить.
- Администратор управляет системой, но по умолчанию не обрабатывает игроков.
- Сотрудники деактивируются, а не удаляются физически.
- Пользователь не может самостоятельно изменить свою роль.

## Доступ и видимость игроков

- Агент видит и изменяет только назначенных ему игроков.
- Агент не может просматривать или изменять чужих игроков и не может переназначать игроков.
- Администратор видит всех игроков и выполняет переназначение.
- Полный номер телефона открывается агенту после действия «Взять в работу».
- Экспорт полного набора контактов доступен только администратору.
- Игроки удаляются только мягко; удаление записывается в аудит.

## Статусы

- `new` — импортирован, но не назначен.
- `assigned` — назначен агенту.
- `in_work` — агент взял игрока в работу.
- `no_answer` — временно не удалось связаться, нужна повторная попытка.
- `success` — окончательная успешная обработка.
- `failed` — окончательная неуспешная обработка.
- `success` и `failed` являются конечными статусами.
- Повторный контакт хранится отдельной датой `follow_up_at` (в текущей модели поля ещё нет).
- Каждое изменение статуса в будущей системе записывается в историю.

## История, комментарии и повторный контакт

- Каждая разрешённая смена статуса создаёт запись с прежним и новым статусом, временем и данными пользователя.
- Запрещённый или отменённый переход не создаёт запись истории.
- Агент добавляет комментарии и управляет следующим контактом только у назначенного ему игрока; администратор — у любого игрока.
- Пустые комментарии запрещены; максимальная длина комментария — 1000 символов.
- `followUpAt` хранит дату и время следующего контакта; отсутствие значения допустимо.
- Фильтры повторных контактов используют локальную календарную дату и время браузера.

## Таблица переходов

| Текущий статус | Следующий статус | Кто может выполнить | Дополнительные условия | Запись в историю |
|---|---|---|---|---|
| `new` | `assigned` | admin | Выбран активный агент; назначение выполняется атомарно | Да |
| `assigned` | `in_work` | назначенный agent; admin | Агент может действовать только со своим игроком; после перехода открывается телефон | Да |
| `in_work` | `success` | назначенный agent; admin | Игрок доступен исполнителю | Да |
| `in_work` | `no_answer` | назначенный agent; admin | Следующий контакт можно назначить через `followUpAt` | Да |
| `in_work` | `failed` | назначенный agent; admin | Окончательный результат | Да |
| `no_answer` | `assigned` | назначенный agent; admin | Возврат в очередь повторной попытки | Да |
| `success` | `in_work` | admin | Явное подтверждение переоткрытия | Да |
| `failed` | `in_work` | admin | Явное подтверждение переоткрытия | Да |

Другие переходы запрещены. Агент не может самостоятельно переоткрыть `success` или `failed`.

## Назначение и деактивация

- Назначения имеют отдельную историю.
- Автоматическое распределение должно выполняться атомарно на сервере.
- Параллельные операции не должны назначать одному игроку двух агентов.
- Деактивация агента не меняет автоматически состояния и назначения его игроков.
- Администратор вручную выбирает игроков для перераспределения.
- Результаты деактивированного агента сохраняются.
- Завершённого игрока переназначает только администратор после явного подтверждения и с записью в историю.

## Импорт и дубли

- Основной ключ дубля — нормализованный телефон.
- При отсутствии телефона используется нормализованный email.
- Дубликат не создаётся.
- Дубли и некорректные строки отображаются в отчёте импорта.
- Каждый импорт имеет отдельную историю.
- Экспорт должен защищать от CSV injection.

## Аудит

Обязательны история статусов, назначений, импортов и административных действий. Мягкое удаление игрока также записывается в аудит.

## Аналитика

- Раздел доступен в клиентском UI только администраторам.
- Текущие статусы и follow-up являются снимком и не зависят от выбранного периода.
- Периодические результаты считаются только по датированным `statusHistory` и `comments`.
- Событийная конверсия определяется как `success / (success + failed)`; при отсутствии терминальных событий она равна нулю.
- Авторы активности определяются по `userId` и `authorId`, а не по текущему назначению игрока.
- Полные определения показателей находятся в `docs/analytics.md`.
