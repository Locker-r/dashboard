# Reactivation Desk: текущее браузерное хранилище

Документ описывает фактическое состояние прототипа на момент выделения data service. Целевые поля и сущности не представлены здесь как уже существующие.

## Ключи и совместимость

| Ключ | Фактическое значение |
|---|---|
| `crm-users` | JSON-массив пользователей |
| `crm-data` | JSON-объект вида `{ "players": [...] }` |

`LocalStorageDataService` сначала пытается прочитать значение через нестандартный `window.storage.get(key, true)`. Полученная строка зеркалируется в `localStorage`. Если host storage недоступно или возвращает неподходящее значение, используется `localStorage`. При записи сервис пытается записать в оба хранилища; операция успешна, если записало хотя бы одно.

Ключи и JSON-форматы не переименованы, поэтому данные прежней версии продолжают читаться. Повреждённый JSON и корректный JSON неправильной формы дают безопасный пустой массив. Автоматическое восстановление или миграция повреждённых значений пока отсутствуют.

## Фактическая модель пользователя

```js
{
  id, username, salt, passwordHash, securitySalt, securityAnswerHash,
  name, role, createdAt, lang
}
```

Фактические роли UI: `admin`, `agent`. Полей активности/деактивации, soft delete и истории нет.

## Фактическая модель игрока

```js
{
  id, phone, email, messenger, status, agentId, importedAt, updatedAt,
  followUpAt, statusHistory, comments
}
```

`followUpAt`, `statusHistory` и `comments` являются необязательными для совместимости с legacy-игроками. При отсутствии массивов UI использует `[]`, при отсутствии или повреждении даты — отсутствие следующего контакта. Истории назначений и импортов, а также soft delete пока нет.

## Центральные функции чтения и записи

- `loadData()` загружает пользователей и игроков через `dataService`.
- `saveDataNow()` сохраняет игроков через `dataService.savePlayers()`.
- `saveUsersNow()` сохраняет пользователей через `dataService.saveUsers()`.
- `saveData()` и `saveUsers()` откладывают запись на 150 мс.
- `flushPendingSaves()` запускает ожидающие записи при скрытии страницы.
- Вход и регистрация передают текущего пользователя в эфемерную сессию data service.
- `logout()` очищает эфемерную сессию.

Data service имеет асинхронный контракт, совместимый с будущим сетевым адаптером. Текущая сессия намеренно хранится только в памяти, как и до рефакторинга, поэтому после перезагрузки требуется повторный вход.

## Где изменяются данные

- Регистрация добавляет пользователя.
- Восстановление, самостоятельная смена и административный сброс меняют пароль.
- Экран доступов меняет роль и физически удаляет пользователя.
- Импорт и одиночное добавление создают игроков.
- Автораспределение и ручное назначение меняют `agentId` и `status`.
- Worklist меняет статус игрока.
- Разрешённая смена статуса добавляет запись в `statusHistory`.
- Worklist добавляет записи в `comments` и изменяет или очищает `followUpAt`.
- Удаление пользователя возвращает его игроков в `new`.
- Dashboard и worklist вычисляют статистику и выборки непосредственно из глобальных массивов.

## Несовпадения с утверждёнными правилами

- Открытая регистрация существует; первый локальный пользователь становится admin.
- Пользователь физически удаляется вместо деактивации.
- Нет защиты последнего администратора.
- Нет истории и аудита.
- Нет soft delete игроков.
- Нет дедупликации и отчёта импорта.
- Round-robin не атомарен и хранит курсор только в памяти.
- Переназначение завершённого игрока не требует подтверждения.
- Клиентские проверки ролей и владения можно обойти.
- Агент может экспортировать свою выборку; полный набор скрыт фильтром UI, а не серверным разрешением.

## Временно небезопасное поведение

Пароли, роли и персональные данные находятся в браузере. Любые проверки в `src/domain.js` и UI являются только единым описанием клиентских правил и не обеспечивают безопасность. Настоящие права, владение игроками, атомарное назначение и аудит должны обеспечиваться backend, RLS и RPC/транзакциями.
